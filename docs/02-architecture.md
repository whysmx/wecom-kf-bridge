# 总体架构

> v0.1。架构约定；cc-connect 具体行为见固定基线契约。

## 1. 三个独立边界

```text
真实企业微信微信客服
    │ 回调 HTTPS，携带加密事件
    ▼
┌──────────── WeCom KF Bridge ─────────────┐
│ 微信客服连接器 → 持久化 Inbox/游标       │
│                         ↓              │
│ 客服/绑定/客户映射 → 人工状态与代际检查   │
│                         ↓              │
│ 加密 XML 投递器 ────────────────────────┼──→ cc-connect 回调
│                                        │          ↓
│ 兼容 HTTP API ←────────────────────────┼─── cc-connect 回答
│          ↓                             │          ↓
│ Outbox/结果登记 → 微信客服发送 API       │      现有 Codex
│                                        │
│ 中文管理页面 / 管理 API / 审计           │
└────────────────────────────────────────┘
```

本网关既是微信客服 API 的客户端，也是 cc-connect 自建应用 API 的兼容服务端，并主动向 cc-connect 发 HTTP 回调。两侧凭证、协议、错误码和消息标识不能直接混用。

## 2. 网络方向

| 来源 | 目标 | 目的 |
|---|---|---|
| 企业微信 | 网关公开 HTTPS 回调 | URL 验证及通知 |
| 网关 | 官方 API | 令牌、消息同步/发送、账号和客户资料 |
| cc-connect | 网关兼容 API | gettoken、user/get、message/send、媒体 |
| 网关 | cc-connect 配置的回调 URL | 加密 XML 问题投递与验证 |
| 管理员浏览器 | 网关管理端 | 配置与诊断 |

cc-connect 机器没有公网地址也可以运行，但网关必须通过同机、可路由内网或受控隧道访问它。不得把 `api_base_url` 解释为反向隧道。

## 3. 同进程模块

| 模块建议名 | 职责 | 禁止职责 |
|---|---|---|
| compat | 现有客户端协议、虚拟令牌、错误转换、XML 投递 | 调用 Codex、猜测客户身份 |
| wechat | 真实微信 API、凭证缓存、官方回调 | 使用虚拟令牌访问官方 API |
| accounts | 客服目录、真实 CRUD、接入链接、绑定 | 改写 cc-connect 文件 |
| identity | 客户映射、昵称缓存、代际 UID | 根据昵称路由 |
| delivery | Inbox/Outbox、游标、重试、UNKNOWN、接管 | 虚构客户端处理完成回执 |
| media | 媒体映射、限额、临时文件清理 | 执行上传文件 |
| admin | 中文管理、鉴权、操作记录 | 暴露真实密钥和客户全文 |
| store/config/security | 事务、迁移、配置、加密、访问校验 | 以通用框架掩盖业务不变量 |

这些是逻辑模块，不要求拆进程。目录可按选定语言调整，但测试覆盖率的业务分组不得在实现后为刷指标任意拆合。

## 4. 数据路径

### 4.1 接收

验证真实企业回调并持久化同步任务，及时响应。独立 worker 以已核实的 token/cursor 作用域分页拉取；一页消息的入库/去重与游标前进在同一事务内提交。按明确 origin/type 处理客户消息、人工消息和事件。只有已绑定、启用且允许 AI 的客户消息进入 XML 投递。

### 4.2 回答

cc-connect 用虚拟凭证获取兼容令牌，令牌明确绑定一个项目接入。`message/send` 校验 agentid、touser、媒体、代际及人工状态；持久化发送记录，再调用真实微信客服 API。默认在客户端预算内等待官方成功/失败结果。超时不等于失败，应标记 UNKNOWN 并返回可诊断的非成功结果。详见可靠性规范。

### 4.3 管理

后台通过账号服务调用真实官方管理 API，操作记录与外部结果分开存储。外部创建成功、本地落库失败不能回滚微信服务器，应保留可恢复操作记录并进行对账。管理和消息不能共享无范围授权的超级令牌。

## 5. 绑定模型

一个客服账号最多有一个 active binding；一个绑定对应一个 cc-connect 的 WeChat Work HTTP 平台实例。不同项目可运行在同一 cc-connect 进程，但其 HTTP 监听端口必须互不冲突。全部绑定可共享网关兼容 API 域名，但虚拟凭证及目标回调独立。

`gettoken` 请求没有 agentid，因此默认每个绑定分配独立虚拟 corp_id/corp_secret（至少 secret 必须唯一），令牌在签发时即确定绑定；禁止之后仅靠消息正文中的 agentid 选择其他绑定。

未知账号不自动挂到默认项目。解绑/改绑采用暂停、处理待发送项、更新 revision/代际、验证、恢复流程，禁止把旧任务改投新项目。

## 6. 并发与部署

单实例优先，SQLite 或等价嵌入式持久化保存状态。每个已确认的拉取 scope 串行推进游标，每个客户会话有序投递；不同会话可由有界 worker 并发。不持有数据库写事务等待网络响应。进程内队列只是加速器，持久化表是恢复来源。

本版不支持多个 worker 实例共用一个未设计抢占租约的数据库；横向扩容需新 ADR。必须支持优雅停止、停止领取新任务、保存执行状态和重启扫描。网络调用通过可替换接口注入，时钟、随机源、重试调度可测试。

## 7. 已知能力损失

现有 HTTP 回调 200 不代表已开始或完成 Codex；客户端发送没有原问题 ID。人工恢复需要使用新代际 UID 防止旧回复混入，相应会产生新 cc-connect 会话。客户端昵称有进程内缓存；网关刷新不强迫客户端刷新。媒体和日志保存不等于允许 Codex 修改项目资料。

这些损失必须进入 UI/运维说明和验收，不能通过隐藏状态、篡改发送时间或修改客户端消除表象。

## 8. 架构验收

未修改客户端用现有表单跑通双向文本；两个以上独立绑定和同名客户隔离；接管后跨代际回复拒绝；重启后游标与任务记录一致；管理 API 越权失败；网关进程无需模型凭证与项目目录访问权限。
