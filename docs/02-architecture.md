# 总体架构

> v0.2。按小项目实施，保留双向协议及持久化，不引入分布式组件。

## 1. 边界与网络

```text
微信客服 --通知--> 网关 --sync_msg--> 微信 API
                    |
                 SQLite
                    |
                    +--加密 XML--> cc-connect HTTP 回调
                    |                   |
                    |                 Codex
                    |                   |
                    <--兼容 API---------+
                    |
                    +--send_msg--> 微信客户
```

网关是微信 API 客户端，也是 cc-connect 兼容 API 服务端；反向主动回调不能省略。公开 HTTPS 接收微信通知；网关出站访问微信 API；cc-connect 出站访问网关 `/cgi-bin`；网关另需访问 cc-connect 回调；管理员只通过本机/受控网络进入管理端。任一方向可通不能证明其他方向可通。

同机或受控内网最简单。跨服务器使用已有私有隧道或受限 HTTPS 反向代理，不开发新的隧道协议。每个客户端 HTTP 平台实例独立监听，同机需不同端口。

## 2. 单进程职责

| 职责 | 内容 |
|---|---|
| 微信适配 | 真实 Token、验签解密、消息同步、发送及账号接口 |
| 兼容适配 | 虚拟凭证、user/get、message/send、XML 回调和媒体映射 |
| 消息与身份 | Inbox/Outbox、游标、路由、代际、人工暂停和失败状态 |
| 账号与管理 | 真实 CRUD、链接、绑定、中文页面、鉴权及操作审计 |
| 基础设施 | SQLite、配置、密钥保护、受控网络、日志和生命周期 |

这是职责划分，不要求五个独立服务或五套框架。小型标准 HTTP 客户端加明确数据类型即可实现已用接口；不引入整个微信 SDK 及其运行时只是为了十几个 HTTP 调用。必要依赖固定版本、检查许可证。

首版按单企业运行，所有授权及标识仍带企业/绑定范围以防错误复用，不增加租户注册平台。一个客服最多一个 active binding；gettoken 没有 agentid，因此每个绑定用独立虚拟 corp_id/secret，在签发时固定 token 范围。禁止仅凭发送体 agentid 切换项目。

## 3. 收发流程

接收通知：验证真实凭证 → 短事务保存待同步标记/拉取材料 → 返回成功。worker 串行推进固定 sync scope，拉取一页后同事务写消息/事件与 next_cursor。通知不是问题正文；只有授权客户内容进入路由。

投递问题：校验绑定、稳定客户权限、人工状态、代际、控制命令策略及媒体可用性 → 持久化投递记录 → 加密 XML。顺序控制只保证网关的出站投递顺序，客户端仍可异步处理；不声称能按 HTTP 200 判断上一轮 AI 已完成。

发送答案：兼容 token/agentid/UID/媒体校验 → 持久化发送记录 → 核查人工、代际和窗口/预算 → 在有界时间内调用官方。官方明确接受才回 `errcode:0`；超时未知保存 UNKNOWN。不在返回失败之后悄悄排队再发一次。

管理操作：同步表单为主，先记录操作及防重复键再调用官方，确定成功才显示成功。未知或进程退出由操作记录核查，不能用分布式回滚假装撤销微信上的已完成操作。

## 4. 存储、并发和恢复

SQLite 是唯一持久化状态源；内存队列仅用于唤醒。单实例启动互斥，重复启动直接失败；不支持多个实例争抢同一个 DB，不引入分布式租约。数据库事务不跨网络调用。

同一同步 scope 串行；同会话的发送授权/代际变化串行裁决；不同客户使用小型有界 worker。建议先从 2 个 worker 起步，属于本地保护值而非用户数量上限，真实吞吐实测后调整。媒体、排队和磁盘同样有界。

停机停止领取任务，尽力完成有限在途操作后保存结果。重启只恢复确定可安全执行的任务；中断 POSTING/SENDING 先判未知，不直接重置 READY。历史补投、发送额度和人工事件缺口遵循[可靠性](07-delivery-and-handover.md)。

## 5. 不做及不保证

不调用模型、不管理 Codex 工作目录，不建坐席聊天、计费、多租户运营、消息中间件或控制平面。管理操作可同步完成就不增加统一异步 202 编排。

不保证重启历史补答、逐问题回传关联、AI 完成回执、恰好一次或跨人工代际无损续聊。头像/昵称更新、媒体失败处理和客户文件隔离均受执行端限制；具体见[技术评审](15-feasibility-review.md)。

验收使用原 R/AT 矩阵及新增 AT-059～AT-069：无修改客户端双向文本、多个绑定/同名客户隔离、旧代际拒绝、事务恢复、管理鉴权、执行端只读与命令权限；均须实际测试。
