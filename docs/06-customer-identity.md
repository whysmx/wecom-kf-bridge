# 客户身份、昵称透传与会话代际

> v0.1。本项目稳定身份设计；外部 nickname 字段及查询条件以 95166 核验结果为准。

## 1. 不要混淆名字与身份

微信昵称仅为显示资料，不保证唯一、固定或是真实姓名。官方客户键按企业范围至少使用 `(tenant_id, external_userid)`；路由与会话还要包含 open_kfid/binding。多个客服遇到同一客户，不得因此进入同一个项目上下文。

正常 AI 接待内为每个 `(binding_id, customer_id, generation)` 分配持久化兼容 UID，例如 `bcu_随机标识_g1`，仅使用安全 ASCII 字符 `[A-Za-z0-9_-]`。不含冒号、逗号、竖线、空白或 `@all`；不从昵称生成。示例后缀可用于调试，实际值应不暴露 external_userid。

内部保留稳定 customer_id。generation 不是每条消息都增长，只有接管恢复、改绑等隔离事件才轮换。兼容 UID 的稳定性在一个代际内成立；发生安全轮换会新建 cc-connect 上下文，这是明确取舍，不得隐瞒。

## 2. 映射流程

```text
真实企业 + open_kfid + external_userid
          ↓ 校验 active binding
稳定 customer_id + 当前 generation
          ↓
兼容 FromUserName / userid / touser
          ↓
cc-connect SessionKey = wecom:{兼容UID}
```

客户端固定源码：[handleMessage / resolveUserName](https://github.com/whysmx/cc-connect/blob/848eb24d89bbd83d03c2afd0dbd94768fd86d5a8/platform/wecom/wecom.go)。HTTP 模式与 WebSocket 模式的 SessionKey 结构不同，不得混用之前讨论的 chatid 方案。

分配 UID 与消息入库要用唯一约束处理并发，重启后读取原映射，不能换随机 ID 造成上下文丢失。防止泄露真实 ID 可以用持久化随机别名，不需要依赖可轮换加密主密钥做会话哈希。

## 3. 客户昵称透传 R-007

官方入口：[客户基础信息 95166](https://kf.weixin.qq.com/api/doc/path/95166)。网关取得客户 nickname 后，通过兼容 GET `/cgi-bin/user/get` 返回 `name`。客户端现有函数会把非空 name 放进 `core.Message.UserName`。

建议在拉取消息后异步/有界预取资料，或首次 user/get 时进行有超时的查询；网关可做批量合并与 single-flight 缓存。不得为每条消息无条件打一次官方资料接口。

成功映射示例：

```json
{"errcode":0,"errmsg":"ok","userid":"bcu_example_g1","name":"小海"}
```

同名客户可以都叫“小海”，但 userid 必须不同。昵称中的表情、非 BMP 字符、换行、HTML 等按普通文本处理；展示时安全转义，不作为 HTML、SQL、日志格式或 Agent 指令执行。

## 4. 缓存和降级

缓存字段包括官方昵称、更新时间、最近成功时间、失效时间、查询状态。建议资料软缓存 6 小时、失败短缓存 1 分钟，均为可配置产品默认而非微信数据有效期；官方允许时间窗口更短时以官方为准。不保留不必要的敏感字段。

查询部分成功逐条更新；一次失败不能清空已有有效昵称，不得使用其他客户的结果。昵称不可得时，兼容响应使用空 name（errcode 为 0），使客户端回退 UID，避免其把“未知客户”这样的占位文字永久缓存。身份不存在/越权则明确报错。

**客户端缓存限制**：当前非空昵称成功解析后存于进程内 userNameCache，没有网关可调用的失效接口。只刷新网关缓存不会立即更新既有客户端显示。管理页应说明“网关资料已更新，cc-connect 可能仍显示缓存昵称”；维护重启或新代际会重新解析，但不得为更新昵称频繁轮换 UID、破坏会话。

不能无证据承诺头像在 cc-connect 中显示；固定函数只读取 name。头像可用于网关中文管理页，但下载/代理必须做 SSRF、容量和生命周期保护。

## 5. 人工接管后的代际栅栏

原协议 `message/send` 没有原问题 MsgId。如果只检查“现在是否人工”，旧 AI 结果可能在人工结束后被误发。本网关采用以下约定：

1. 观察到或主动发起人工接管时，先封锁当前代际的出站资格，停止新 AI 投递。
2. 人工结束后，只有官方状态允许且管理员/已确认规则允许恢复时，创建 generation+1 和新兼容 UID。
3. 后续问题使用新 UID；旧 UID 及其既有 outbox 永久不得重新具备发送资格。
4. 旧 UID 发来的回复返回非成功状态并记录 stale_generation，不能自动改成新 UID。

由此带来的新会话无法自动继承旧 cc-connect 对话；本项目不修改其数据库、不拼接伪系统提示自动迁移上下文。需要保留历史上下文的另一种方案必须另行评审，不能声称本版同时做到严格隔离和无损跨代际续聊。

已提交到官方的在途消息无法靠网关追回；接管时间竞态见可靠性文档。停止发送不等于停止 Codex 计算。

## 6. allow_from 与管理权限

正常 UID 在同一代际内可使用 cc-connect allow_from。轮换代际后，显式 UID 白名单/管理员 UID 需要同步更新。不能为绕过白名单而冒用另一用户 ID。

更适合本方案的部署是网关对稳定 customer_id 做入口授权，而 cc-connect 仅接收受保护网关的回调；是否允许 `*` 由管理员明确配置。客户消息入口不得获得跨会话管理、修改模式或服务器命令权限。项目目录共享不代表允许每位客户浏览他人附件或所有历史；执行端权限仍需独立验收。

## 7. 测试

同名两客户、同客户两客服、跨企业相同 external_userid、昵称改变、空昵称、表情/恶意字符、批量部分失败、并发首次资料查询、缓存时间边界、重启映射稳定、旧 UID 发送、接管恢复后新 UID、显式白名单轮换均必须测试。报告区分“消息 UserName 字段透传”和“所有 UI 立即显示新昵称”，后者不属于无条件保证。
