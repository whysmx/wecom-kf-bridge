# 消息可靠性、状态机与人工接管

> v0.1。本版不宣称端到端 exactly-once。区分已持久化、HTTP 已接受、官方已接受、客户已读；现有协议无法证明的状态必须保留为未知。

## 1. 核心不变量

- 未通过验证的通知不触发业务；Inbox 入库与游标更新必须原子提交。
- 每个官方消息键只产生一个正常 Inbox 记录；每次兼容回调重试沿用同一 MsgId。
- 发送必须同时满足企业权限、active binding revision、有效 UID generation、可发送的官方状态及平台窗口。
- 人工、停用、旧代际或不明确状态下默认不发送 AI 回答。
- 本地确认成功不能先于相应外部证据；结果未知不能当成未发生。

## 2. 接收通知与同步任务

真实回调校验成功后，将需要拉取的通知材料持久化，再回复规定成功响应；持久化失败不返回虚假成功。重复通知合并同一 scope 的拉取任务，任务可重复执行，消息本身由唯一键去重。

worker 在同一 sync_scope_key 上串行：读 cursor → 调用官方 → 数据校验 → 事务写本页 Inbox/事件并更新 next_cursor → 根据 has_more 继续。网络请求不在数据库写事务中等待。断电发生在提交前则重拉该页，发生在提交后则从新游标恢复，两种都不得丢页。

未知/不支持事件也须有可追踪记录，不能因为无法处理就一直卡住拉取游标。处理策略可标 quarantined，再推进持久化页；数据损坏且无法确定消息边界时则暂停 scope。

## 3. Inbox 状态

```text
RECEIVED → CLASSIFIED → READY → POSTING → HTTP_ACCEPTED
               │          │       ├→ RETRY_WAIT（明确未接受）
               │          │       └→ DELIVERY_UNKNOWN（可能已接受）
               │          ├→ HELD（人工/停用/权限待确认）
               │          └→ EXPIRED（超时/历史过滤）
               └→ IGNORED / UNSUPPORTED
```

HTTP_ACCEPTED 仅表示目标 HTTP 返回成功，不能改名为“已回答”或“已处理”。固定 cc-connect 回调在业务处理前即可写 200，也可能随后过滤旧消息/未授权用户。管理员页面应显示最后一次目标响应及诊断提示。

对 connection refused 等可证明未投递的失败进行有界重试；发送请求后断线无法证明是否处理，标 DELIVERY_UNKNOWN。可按已验证的客户端短去重窗口有限重投同一 MsgId，但窗口外默认不自动重投，需人工确认重复风险。不得靠改时间绕过客户端旧消息过滤。投递有效期必须同时考虑客户端阈值和官方回复窗口，在 P0 固定。

## 4. Outbox 状态与兼容应答

```text
CREATED → VALIDATED → SENDING → UPSTREAM_ACCEPTED
              │         ├→ RETRY_WAIT（确定无副作用且可重试）
              │         ├→ UNKNOWN（可能已被官方接受）
              │         └→ REJECTED（明确永久失败）
              └→ BLOCKED（权限/停用/人工/旧代际/超窗）
```

每次收到兼容 `/message/send` 请求分配 outbox_id 并持久化请求摘要、绑定/客户/代际、消息内容受保护引用，随后在有界时间内向官方发送。建议单次同步预算 15 秒，须低于固定客户端 30 秒 HTTP timeout；预算为本网关设计值，实际按环境联调。

官方返回成功才对客户端 `errcode:0`。官方错误返回明确网关错误；截止时间耗尽但网络结果不确定时返回非零 UNKNOWN，并保留记录。请求的取消不应抹去已提交外部请求的结果；服务端后续确定结果应更新 outbox，但不能假装客户端已经看到了该结果。

没有固定客户端请求幂等键，网关无法可靠区分“同内容合法发送”与“客户端/代理重试”。禁止以内容哈希或 N 秒窗口无条件去重，否则合法的相同回答会被吞掉。为自己的同一 outbox 重试使用稳定发送标识；官方是否真正支持去重须核验。没有明确幂等保证时，对 UNKNOWN 不自动重发。

客户端分块产生多个请求，网关不知道整份回答边界。保留请求顺序；部分分块成功部分失败时显示部分发送，不拼造“完整发送”。不能由网关自动把缺失片段转给另一个客服补发。

## 5. 人工状态与本地栅栏

本网关状态名：AI_ELIGIBLE、WAITING_HUMAN、HUMAN、CLOSED、UNKNOWN；官方数字值在微信适配层单点映射。状态来源、更新时间和本地 fence_version 单独存储。

客户主动转人工或管理员发起接管时先建立本地发送栅栏，再尝试官方转换；官方失败仍保持暂停并报告需处理，不能自动放行 AI。通过企微原工作台接管时由事件更新，并在每次发送前核查官方状态弥补事件延迟。核查失败默认 BLOCKED。

接管后停止新客户问题发往 Codex，已有任务可能继续运行，但网关不发送其结果。不要伪装一个 `/stop` 客户问题来取消任务，也不要给网关执行 cc-connect 管理命令的隐藏权限。

恢复必须确认官方状态允许，并创建新 UID generation；旧代际出站永远失效。详见 [身份文档](06-customer-identity.md)。默认不自动补送人工期间/停用期间积累的历史问题。

## 6. 不能消除的竞态

“最后一次状态检查”和“官方实际发送”不是一个跨系统原子事务。若官方已经接收发送请求后才发生接管，网关无法撤销该条在途消息。文档与测试应区分：

- 接管栅栏提交前尚未发送：必须被后续栅栏阻止。
- 接管栅栏提交后发起的新请求：必须阻止。
- 接管发生时已在官方处理的请求：记录 in_flight_at_handover，不能保证撤回。
- 人工结束后到达的旧 AI 回复：通过旧代际 UID 必须阻止。

本地对同会话发送/状态变更使用短临界区或版本检查，不能在数据库锁内等官方网络。外部状态无法确认时优先不发；不要宣称“任何时间绝对零抢答”。

## 7. 重试与错误分类

| 类别 | 建议动作 |
|---|---|
| 鉴权失效且确认请求未执行 | 刷新令牌后最多一次立即重试；并发刷新合并 |
| 确定未连接/读操作暂时失败 | 指数退避加抖动，有总时限 |
| 限流 | 按官方建议等待，保留顺序，不能绕过 |
| 无权限/参数错/不支持类型/超窗 | 不自动重试，提示管理员 |
| 写接口响应丢失/无法确认 | UNKNOWN，核查或人工决策 |
| 账号删除/旧 binding/旧 UID | BLOCKED，不重投到新映射 |
| 数据库磁盘满/损坏 | 停止承诺接受新任务，健康状态异常 |

默认退避、最大尝试和有效期须可配置并可注入时钟测试；不得永远重试。管理账号 add/delete 等副作用请求与文本发送共享“不确定结果不得盲重试”的原则，但它们各自有独立状态记录。

## 8. 重启恢复与审计

重启只重新领取已到期租约且可安全重试的任务。SENDING/POSTING 中断先进入待判定，不直接重置 READY。UPSTREAM_ACCEPTED 不能重新发送。游标与消息唯一键必须恢复到一致快照；恢复旧备份时默认维护模式，先与官方/发送记录对账，避免重发已送消息。

审计使用 trace_id、notification_id、inbox_id、outbox_id、binding_id/revision、脱敏 customer 标识及错误类别。敏感正文与令牌不得进入结构化日志。指标不能以 customer ID/消息 ID 为无限维度标签。

## 9. 必测故障注入

入库前/事务中/事务后退出；下一页拉取失败；重复/乱序/未知事件；回调接受后目标进程退出；官方已接受但响应丢失；相同内容的两次合法发送；接管中/恢复后旧结果；改绑后旧令牌；过期媒体；停用恢复历史消息；数据库满/备份回滚。测试必须同时断言状态、外部调用次数和“不应产生的副作用”。
