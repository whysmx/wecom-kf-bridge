# 开发阶段、任务与 Agent 交接

> v0.1。这里只规划，不包含业务实现。任务完成需要实际证据，不以文件数量或已写函数数量计进度。

## 1. 阶段顺序

```text
P0 契约/工具链冻结
  ↓
P1 可测试骨架与安全/持久化基础
  ↓
P2 未修改 cc-connect 的文本兼容闭环
  ↓
P3 微信客服真实接入/身份/可靠性
  ↓
P4 真实客服账号管理及中文界面
  ↓
P5 媒体/人工接管/恢复/安全补齐
  ↓
P6 全量测试 >95% /Windows 联调/发布验收
```

账号服务可在 P2 后按冻结合同并行，但真实管理发布依赖 P0 权限核验。不得先建完整管理站再验证 cc-connect 能否通过现有配置收发。

## 3. 每个阶段的退出标准

P0：所有要实现的官方接口有权威契约/样本；不可读或权限缺失的项目列出 blocker；语言/版本/依赖、错误语义、数据字段和测试范围经评审。不能只填一串 API 名称宣布完成。

P1：没有真实凭证也能启动隔离测试；数据库/密钥/错误路径可注入；第一段生产代码合并即受覆盖率约束，不能把指标拖到项目结束才补。

P2：网关主动向真实固定适配器发送加密 XML，客户端可解析 UserName 并按现有 API 回答；通过原 GUI 的字段映射验证；没有修改客户端。

P3：微信客户文本闭环通过，重复回调/多页/崩溃可恢复；消息状态不冒充处理完成；名字与身份隔离。

P4：管理的确改变官方客服账号，而不只是本地行；重复提交、UNKNOWN、删除/解绑区别及配置导出完整；没有创建其他运营功能。

P5：媒体方向和错误明确；人工接管后旧代际结果被拒绝；所有危险路径可测试；无法消除的在途竞态在页面/手册说明。

P6：全量报告原始覆盖率 >95%，矩阵全部有证据，Windows 和真实微信联调/恢复通过，未决阻塞清零或明确不发布该能力；没有“先发版以后补测”。

## 4. 多 Agent 工作边界

建议只在契约冻结后并行：连接器 Agent 负责微信适配；兼容 Agent 负责 cc-connect 协议；管理 Agent 负责账号/UI；测试 Agent 独立审查协议/安全/门禁。数据模型、错误码、UID 和状态机由统一负责人维护，不能每人各写一套。

每项任务说明允许修改目录、依赖提交 SHA、需要的接口和测试编号。修改共用契约先通知其他任务；不得覆盖未完成的他人改动，不以复制逻辑解决循环依赖。PR 只承载一个可验收能力。

## 5. 防止跑偏的检查问题

实现是否仍使用截图中 HTTP 表单？是否误用 ws_url？是否偷偷改了 cc-connect？是否把真实 Secret 分发给客户端？是否只做本地 CRUD 没调用官方？是否遗漏客户昵称？是否写死账号数量？是否用昵称当 ID？是否将 200 或请求入队当“已送达”？是否对 UNKNOWN 自动重复建账号/发消息？是否把空测试报告当 100%？

任何一项命中都不能进入下阶段。新增 UI 功能、服务依赖、默认策略或平台限制必须有需求/证据，不接受“为了以后扩展”而增加无关框架。

## 6. 交接格式

每次交付包含任务 ID/需求 ID、实现与未实现清单、契约变更、修改文件、实际测试命令/结果/报告、覆盖率分母、官方核验记录、环境配置步骤及遗留风险。使用任务和测试报告模板，不用“应该可以”“大概率正常”作为完成证据。
