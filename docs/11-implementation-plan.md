# 最小实现顺序与交付

> v0.2。任务仍待实现；按可验收能力逐步推进，不把文档数量当进度。

## 1. 顺序

```text
P0 固定当前能力合同与最小互操作验证
 ↓
P1 可测试骨架、SQLite、鉴权与命令限制
 ↓
P2 文本闭环 + 身份/昵称 + 人工暂停/代际 + 故障可见
 ↓
P3 真实客服管理 + 简单中文页面 + 绑定
 ↓
P4 媒体、运维、恢复和完整发布验收
```

原 P5 才开始人工接管的安排取消。首次允许真实客户访问文本入口前，人工暂停、旧代际拒绝、控制命令限制、发送预算、持久化和安全配置必须具备。可以先在隔离 fake 环境写文本兼容实验，但不能把无安全边界的实验当可对外试用版本。

默认一个实现者顺序完成小切片。没有实际需求不拆微服务、不启用多 Agent 组织、不先做完整后台或通用测试平台。原媒体/账号/测试需求不删减；只通过文本不代表完整首版完成。

## 2. P0：先证实可以接，再做其余功能

固定上游客户端 SHA 和运行版本，先用未修改的 HTTP 适配器加独立测试 handler 验证挑战、加密 XML、token、user/get、message/send。适配器 harness 不等于完整 GUI/Codex E2E，报告分开写。

按当前切片核验官方/企业合同：文本先确认凭证、回调、sync scope、状态、send policy；头像/账号管理/媒体的细则可以在对应阶段前补齐。不要求全部外部页面可读才能建立测试骨架，但相应真实能力发布前不得保留未知的关键权限或限制。

参考栈仍是 Go/SQLite/内嵌 HTML。首次实现记录工具链、驱动、必要依赖/许可证和 Windows 条件；不要为“以后扩展”换成更复杂技术栈。

## 4. 每阶段退出条件

P0：不是只列 API 名称，而是至少有固定客户端协议证据和可以执行的最小互操作实验；剩余官方核验按受影响能力列出。源码检查、fake、适配器运行、真实企业运行分栏，不互相替代。

P1：没有真实凭证也能测试，持久化和网络错误可注入；第一段业务代码即纳入覆盖率和关键场景测试。单实例互斥，不建立分布式 lease。

P2：未改客户端收发文本，昵称回退正常，多个客户/绑定隔离；重复通知、分页和两侧重启行为有测试；人工/停用/旧代际不发送；控制命令不能使客户管理任务或改变执行权限。实测窗口/预算和运行账户后才允许受控真实文本试用。

P3：真实官方账号 CRUD/链接有效，而不是只更新 SQLite；重复创建/外部未知/删除确认/列表部分失败可控。中文页面同步操作优先，状态清楚，不先建设通用异步平台。所有读取也鉴权。

P4：既定媒体方向逐项测试，不支持的类型明确标记未完成；真实微信 → 网关 → 原版 cc-connect → Codex → 微信，以及真实管理操作、Windows 运行、备份恢复和关键安全场景通过。整体/每模块及原约定口径严格 >95%，才可声明完整首版完成。

## 5. 测试与交接

继续遵守[测试门禁](10-testing-and-coverage.md)，不降低阈值、不删异常用例、不把 Go 语句覆盖冒称分支覆盖。优先标准 Go 工具及一个小型门禁脚本；门禁自身负向测试仍保留，但不用先建设独立覆盖率服务或全面 mutation 平台。

一次任务交付包含 R/T/AT 编号、改动文件、实际命令与结果、原始覆盖率、未测/失败项及来源差异，模板可简短填写。业务实现、测试、文档可在一个小任务提交中一起交付；严禁虚报“应该通过”。

新增依赖、扩大权限、改变 UID/恢复语义或降低原功能/质量要求必须评审。源码限制不得靠修改 cc-connect 隐藏。若确实需要并行，只围绕已冻结契约划分小范围，不让多个实现者各造一套状态机。
