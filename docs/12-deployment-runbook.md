# 部署、配置与运维手册（待实现版）

> v0.1。本文件规定实现后的操作流程；仓库现在没有可下载运行程序，文中的域名、端口和键值只是示例。

## 1. 部署前置

准备企业微信管理员权限及可调用微信客服接口的凭证；确认账号处于可 API 管理/可见范围。准备网关公开 HTTPS 回调和官方 API 出站连接；cc-connect 所在 Windows 机器安装并配置原有 Agent，只给指定项目资料问答权限。

网关访问 cc-connect 需要实际网络可达。最简单是同机/受控内网，跨服务器则配置 VPN/私有隧道或只允许网关访问的 HTTPS 反向代理。客户端端口无需向所有公网开放。

“可访问外网”“有公网 IP”“公开 HTTPS 回调可达”“网关到客户端可达”分别验收，不能用一次 ping 代替。

## 2. 首次初始化顺序

1. 部署已构建网关，设置独立服务账户、数据目录、外置主密钥、管理访问控制。确认备份不会同时泄露主密钥。
2. 登录中文后台添加真实企业配置，验证凭证/权限，配置企业微信官方回调到 `/webhooks/wechat-kf/{tenant_key}` 并通过验证。
3. 同步真实客服账号或显式创建测试客服，取得 open_kfid。账号先保持网关转发停用。
4. 给账号创建 binding，填写 cc-connect 的完整 callback_url，生成虚拟企业/应用/密钥和回调加密参数。
5. 在 cc-connect 项目里选择 WeChat Work 手动配置，按下表填入。启动对应平台监听。
6. 回到网关做加密 echostr 验证，确认真实解密回显；启用转发，再由测试微信用户发送无敏感问题。
7. 验证回复、昵称、项目对应、不同客户隔离和人工接管；正式启用前完成验收报告。

## 3. cc-connect 现有表单字段对照

| 表单字段 | 来源/示例 |
|---|---|
| 企业 ID | 网关分配的虚拟 corp_id，不直接复制真实企业配置 |
| 企业密钥 | 网关分配的绑定密钥 |
| 应用 ID | 网关分配的数字 agent_id，例如 1000002 |
| 回调 Token | 网关绑定的 callback_token |
| 回调 AES Key | 网关生成的合法 43 字符 key |
| 端口 | 本机监听，例如 8081 |
| 高级 → 回调路径 | /wecom/callback |
| 高级 → API 基础地址 | https://bridge.example.com |
| 高级 → 允许的用户 | 明确授权的兼容 UID；允许全部映射客户时由管理员决定使用 * |

高级地址不带 `/cgi-bin/gettoken`；网关会提供这些兼容路径。该配置是 HTTP 自建应用模式，不填 BotID/ws_url，不使用 WeChat 扫码，不需要真实智能机器人账号。

网关的 callback_url 同机示例：`http://127.0.0.1:8081/wecom/callback`；不同主机填写网关实际可达地址，而不是浏览器所在机器的 localhost。

多个同机项目分别用 8081、8082 等空闲端口；示例数量不是上限。填写不同 callback_path 但相同 port 不能解决多个 HTTP 服务绑定冲突。不同绑定可共享网关 API 域名，但不得共用身份/密钥导致跨项目路由。

## 4. 只回答部署

保持模型和第三方中转站配置在 Codex/cc-connect 原位置，网关不需要 API Key。选择实际固定版本支持的只读模式并验证，限制写入型工具/MCP、目录、命令、跨会话管理及网络访问。

项目资料可以只读，但 cc-connect/Codex 仍可能需要写日志、会话、缓存和附件。把运行时数据目录与只读资料分开，不能为了“只读”导致附件接收崩溃，也不能为了写附件给整个项目管理员权限。

普通客户不应获得切换权限模式、读取他人会话、修改工作目录或部署等管理命令。验证网关稳定客户授权与兼容 UID 白名单；接管恢复产生新 UID 时要同步显式白名单。用户昵称不是管理员身份凭据。

## 5. 日常诊断

| 现象 | 检查顺序 |
|---|---|
| 微信回调验证失败 | 公网 HTTPS/DNS/证书 → 反代路径/请求体 → 官方回调 Token/AES/receiver |
| 通知正常但没正文 | sync scope、Token/cursor、权限、分页错误、事件 origin/type |
| 网关有问题但 cc-connect 无响应 | binding启停 → 回调目标可达 → 挑战验证 → XML/MsgId/时间/allow_from → 客户端日志 |
| 网关回调 200 但没回答 | 200 不是处理完成；检查旧消息过滤、授权、Agent 错误/只读/工作目录 |
| 回答发送失败 | api_base_url → 虚拟 token → agentid/UID scope → 人工/代际 → 官方权限/窗口/额度 |
| 昵称未变化 | 网关资料/缓存 → 客户端非空 name 进程缓存；不是改 nickname 生成新 ID |
| 多项目端口冲突 | 客户端各实例监听端口及已有服务；不在网关写死五个监听器 |
| UNKNOWN | 先核实官方/目标实际效果，不立即点击连续重试 |

健康检查建议 `/health/live` 表示进程可响应，`/health/ready` 表示数据库/配置可服务；公开健康只返最少字段。管理页单独展示真实企业接口、绑定回调与消息状态，不能把第三方偶发超时一律变成进程死亡重启。

## 6. 日志与指标

记录脱敏 trace/inbox/outbox/operation/binding ID，保留错误类型及关键时间。监控：拉取延迟、游标停滞、待处理队列长度、回调失败、官方发送接受/拒绝/UNKNOWN、人工抑制、账号不可见、磁盘/媒体空间、令牌刷新失败。

不在 URL 访问日志记录 corpid+corpsecret、access_token 或拉取 Token。不开常态正文 debug。指标标签不包含无限增长的客户/消息 ID。

## 7. 备份、升级与恢复

先停止领取或进入维护模式，完成一致性数据库/媒体备份并记 schema/程序版本；验证主密钥恢复方式。升级测试环境，跑迁移、客户端契约和恢复测试，再在维护窗口部署。不得用强制启动绕过迁移失败。

恢复旧备份后默认暂停官方写操作和客户投递：可能存在备份时间之后已经成功发送/创建的外部副作用，先同步核查，不自动从旧游标重放所有数据。未知 operation/in-flight 记录按可靠性文档处置。

升级 cc-connect 时保持其源码不变，先验证新版本 HTTP 字段、响应解析、媒体、用户名缓存、旧消息规则和表单，再更新兼容矩阵。不要自动跟随 latest/main。

## 8. 发布检查

测试证据与覆盖率 >95%；官方权限/限制已核验；真实账号 CRUD/链接/问答通过；Windows 原生执行验证；人工接管及新代际恢复已告知；账号数量无硬编码；备份恢复完成；无真实数据入库仓库；所有示例凭证已替换且密钥不公开。
