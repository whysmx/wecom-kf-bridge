# ADR-0001：首版边界与实现基线

- 日期：2026-10-09
- 状态：产品路线已按用户要求确定；实现栈建议待 P0 评审。
- 关联：[需求](../01-requirements.md)、[架构](../02-architecture.md)、[依据](../14-sources-and-verification.md)。

## 背景

用户要独立开发微信客服 → 网关 → cc-connect，并使用现有 WeChat Work 表单高级 API 基础地址，不修改 cc-connect 源码。后来明确新增客服账号管理、客户昵称透传及测试覆盖率 95% 以上。不固定客服/用户数量，不建设复杂客服运营平台。

## 决策一：HTTP 自建应用兼容，而不是 WSS

网关对 cc-connect 暴露 gettoken、user/get、message/send、媒体接口，并向其回调 URL 投递加密 XML。对微信侧处理真实客服回调及 API。

原因：与已核对表单及 api_base_url 行为吻合；无需新字段/插件/源码修改。代价：网关必须能访问客户端回调；多项目需要避免监听端口冲突；协议缺少原问题 ID 和处理完成回执。不得把这些代价靠隐性修改客户端解决。

拒绝方案：主线改为智能机器人 WSS、OneBot、个人微信扫码；直接在 cc-connect 新增 wecom_kf 平台；单纯反向代理不做内容转换。

## 决策二：保留轻量账号管理

同一网关内提供中文管理页面和私有管理 API，只管理真实客服账号、绑定、凭证、启停、接管诊断与审计。不做工单/排班/计费/注册租户/模型配置。

这是新增“客服账号管理”需求所必需的管理能力，不等同于重建客服工作台。只实现本地配置 CRUD 而不提供真实官方账号操作不能验收。

## 决策三：持久化优先但不引入分布式平台

建议单实例网关、SQLite、同进程 worker；Inbox/游标/Outbox/操作状态/身份映射持久化。队列不能只存在内存；也不默认引入 Redis/Kafka/Kubernetes。

真实外部写接口无法回滚时用操作记录和对账，结果未知就明确 UNKNOWN。不追求无法由现有协议保证的 exactly-once。

## 决策四：身份与人工隔离

稳定 customer_id + 绑定 + generation 映射为兼容 UID；正常对话不变，人工恢复/改绑时轮换。旧代际不再发送，从而避免人工结束后旧回答误入。代价是 cc-connect 会创建新上下文，不能无改源码自动拼接以前会话。后续要改善必须新 ADR，并证明不会重引入旧回复风险。

## 决策五：推荐 Go 实现，未擅自认定用户选栈

建议 Go 服务端、SQLite 和内嵌轻量中文 HTML 页面，减少部署组件；使用标准 HTTP/JSON/XML/密码库，必要依赖最少化并固定版本。核心逻辑与网络/时钟/存储分离以便覆盖率测试。

用户并未指定语言。P0 记录最终 Go 版本、数据库驱动、UI 方案、Windows 支持、测试/覆盖工具及许可证。若所有者选择 .NET 等其他栈，可保持产品/协议/数据/测试目标不变，先更新 ADR 与工具命令；不得把推荐 Go 当作取消用户偏好的硬约束，也不能未经评审来回换栈。

不在文档阶段添加未经验证的 go.mod、可运行服务或依赖锁文件。仓库尚无许可证时由所有者选择；引用上游接口不等于可以无视其许可证复制大量实现。

## 决策六：质量门禁不可降级

服务端整体/每模块/新增修改语句 >95%；关键场景全通过；前端业务逻辑单列；不得把 Go 语句覆盖叫分支覆盖。没有生产代码或原始报告时标未测。门禁实施和平台分支保护设置另有实际任务，文档提交不等于 CI 已启用。

## 变更流程

更改网络模式、账号能力、身份代际、可靠性承诺、实现栈、外部依赖或覆盖门槛，须新 ADR 列原因、影响、迁移和测试，经所有者评审后更新需求/契约/矩阵。禁止 Agent 以实现方便为由直接修改本 ADR 的结论。
