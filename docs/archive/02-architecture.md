# 总体架构

> 当前最终设计 · 2026-10-09。一个网关进程并发服务多个客户，保留双向协议及持久化，不引入分布式组件。

## 1. 边界与网络

```text
客户 A ─┐
客户 B ─┼─ 微信客服 ─ 网关（单进程、并发处理） ─ cc-connect ─ Codex
客户 C ─┘                   ↕
                          SQLite
```

网关是微信 API 客户端，也是 cc-connect 兼容 API 服务端；反向主动回调不能省略。公开 HTTPS 接收微信通知；网关出站访问微信 API；cc-connect 出站访问网关 `/cgi-bin`；网关另需访问 cc-connect 回调；管理员只通过本机/受控网络进入管理端。任一方向可通不能证明其他方向可通。

同机或受控内网最简单。跨服务器使用已有私有隧道或受限 HTTPS 反向代理，不开发新的隧道协议。每个客户端 HTTP 平台实例独立监听，同机需不同端口。

## 2. 单进程与多客户并发

**单进程只表示运行一个网关服务，不是单线程、单任务或单客户。** 多个 HTTP 请求和后台任务可在进程内并发执行；采用 Go 时可用标准 HTTP 服务、goroutine 和有界任务调度实现，无需为每位客户新起一个网关。

客户 A 发起较慢的问题后，网关投递完成即释放对应投递任务，不占着全局 worker 等待 A 的 AI 回答；这时 B、C 仍可进入各自会话。cc-connect 后续通过独立请求回传答案。网关本身不运行 Codex，也不把所有执行端限制成一个进程或一轮对话。

| 范围 | 并发规则 |
|---|---|
| 不同客户，含同一客服/项目中的不同客户 | 独立 UID/会话并发收发；A 的长回答不应因网关全局锁阻塞 B |
| 同一客户会话 | 按需要有序投递；发送资格、人工栅栏、代际及预算更新局部串行，不阻塞其他客户 |
| 同一 sync scope 的游标 | 串行分页/提交，避免游标竞争；不等于客户对话全部串行 |
| 不同同步 scope 或绑定 | 在配置的资源上限内并发，无跨绑定身份复用 |
| SQLite 写事务 | 保持短事务，不持写锁等待 HTTP 或 AI；不把事务串行性延伸为整轮对话串行 |

网关不能仅凭多个 handler/goroutine 就宣称整个 AI 链路已实现某个并发容量。实际 cc-connect/Codex 配置、运行资源和平台限额仍须验证；同项目和不同项目都纳入 AT-070。执行端存在全局串行瓶颈时必须记录并解决部署/配置问题，不能用网关并发假装端到端并发已通过。

## 3. 同进程职责

| 职责 | 内容 |
|---|---|
| 微信适配 | 真实 Token、验签解密、消息同步、发送及账号接口 |
| 兼容适配 | 虚拟凭证、user/get、message/send、XML 回调和媒体映射 |
| 消息与身份 | Inbox/Outbox、游标、路由、代际、人工暂停和失败状态 |
| 账号与管理 | 真实 CRUD、链接、绑定、中文页面、鉴权及操作审计 |
| 基础设施 | SQLite、配置、密钥保护、受控网络、日志和生命周期 |

这是职责划分，不要求五个独立服务或五套框架。小型标准 HTTP 客户端加明确数据类型即可实现已用接口；不引入整个微信 SDK 及其运行时只是为了十几个 HTTP 调用。必要依赖固定版本、检查许可证。

首版按单企业运行，所有授权及标识仍带企业/绑定范围以防错误复用，不增加租户注册平台。一个客服最多一个 active binding，但可同时服务多个客户；一个 binding 对应平台接入，不是一个客户名额。gettoken 没有 agentid，因此每个绑定用独立虚拟 corp_id/secret，在签发时固定 token 范围。禁止仅凭发送体 agentid 切换项目。

## 4. 收发流程

接收通知：验证真实凭证 → 短事务保存待同步标记/拉取材料 → 返回成功。同一 scope 的同步任务串行推进游标，拉取一页后同事务写消息/事件与 next_cursor。通知不是问题正文；只有授权客户内容进入路由。

投递问题：校验绑定、稳定客户权限、人工状态、代际、控制命令策略及媒体可用性 → 持久化投递记录 → 加密 XML。不同客户独立调度。同一客户的顺序控制只保证网关的出站投递顺序，客户端仍可异步处理；不声称能按 HTTP 200 判断上一轮 AI 已完成。

发送答案：兼容 token/agentid/UID/媒体校验 → 持久化发送记录 → 核查人工、代际和窗口/预算 → 在有界时间内调用官方。官方明确接受才回 `errcode:0`；超时未知保存 UNKNOWN。不在返回失败之后悄悄排队再发一次。

管理操作：同步表单为主，先记录操作及防重复键再调用官方，确定成功才显示成功。未知或进程退出由操作记录核查，不能用分布式回滚假装撤销微信上的已完成操作。管理网络等待不持全局消息锁。

## 5. 存储、资源边界和恢复

SQLite 是唯一持久化状态源；内存队列仅用于唤醒。单实例启动互斥，重复启动直接失败；不支持多个网关实例争抢同一个 DB，不引入分布式租约。数据库事务不跨网络调用。

不同客户使用有界后台任务。配置示例的 2 个 worker 只表示该类网关任务最多同时执行 2 个，**不是最多 2 个客户，也不是最多 2 个正在生成回答的 AI 会话**。投递 worker 不等待整轮 AI，回传由独立 HTTP 请求处理；所有网络请求均有超时。真实负载下按容量调整 worker 与请求并发限制，不写死客户数。

容量不足允许短时有界排队；队列满、慢回调、单客户连续消息等必须有明确策略和诊断，不无限积压，也不通过为每个客户拆微服务解决。并发上限、排队、媒体、图片像素和磁盘均有界；这与允许多客户同时对话并不矛盾。

停机停止领取任务，尽力完成有限在途操作后保存结果。重启只恢复确定可安全执行的任务；中断 POSTING/SENDING 先判未知，不直接重置 READY。历史补投、发送额度和人工事件缺口遵循[可靠性](07-delivery-and-handover.md)。

## 6. 不做、不保证及验收

不调用模型、不管理 Codex 工作目录，不建坐席聊天、计费、多租户运营、消息中间件或控制平面。管理操作可同步完成就不增加统一异步编排。

不保证无限并发、重启历史补答、逐问题回传关联、AI 完成回执、恰好一次或跨人工代际无损续聊。头像/昵称更新、媒体失败处理和客户文件隔离均受执行端限制；具体见[技术评审](15-feasibility-review.md)。

验收覆盖无修改客户端双向文本、多客户并发、多个绑定/同名客户隔离、旧代际拒绝、事务恢复、管理鉴权、执行端只读与命令权限。AT-070 使用单个网关进程，验证同项目/不同项目多个客户同时提问、A 慢 B 快、无串话、同会话局部顺序及达到容量边界的行为；这些都是待执行要求，不是现有性能测试结果。
