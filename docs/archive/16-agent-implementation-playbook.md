# Agent 实现手册与偏移防护

> 本文是后续实现 Agent 的执行入口。它不能替代需求、契约、架构、可靠性和测试文档；发生冲突时，以 `AGENTS.md` 及各专题文档中的当前设计为准。

## 1. 开发前必须确认的边界

1. 产品链路固定为：个人微信客户 → 企业微信微信客服 → 本网关 → 未修改的 cc-connect WX / WeChat HTTP 适配 → Codex。
2. 不修改 cc-connect，不新增 cc-connect 平台插件，不改成智能机器人 WebSocket、个人微信扫码、OneBot、TG 或 Slack。
3. 网关不调用模型、不运行 Codex、不保存 Codex 凭证和项目目录；它只做协议转换、身份路由、状态持久化和企业微信 API 调用。
4. 一个网关进程必须同时服务多个客户。不得使用包级全局锁、单一等待队列或“一个 AI 完成后才能处理下一个客户”的设计。
5. 客服账号数量、客户数量、项目数量都不能写死。每个客服账号与项目的绑定关系必须显式、可审计、可变更。
6. `95166` 是客户资料/昵称相关依据，不是客服账号管理接口。客户不能按昵称识别。
7. 文档中的 fake、SDK 源码和契约测试不能冒充真实企业微信联调；未执行的验收项必须标记为 blocked 或未测。

## 2. 实现顺序

按以下顺序逐个交付可验证切片，不要先搭建没有验收标准的“大而全”平台：

- P0：固定 cc-connect 兼容合同、微信客服字段和待核验外部约束。
- P1：配置、启动/关闭、SQLite 迁移、鉴权边界、日志、健康检查和可注入网络接口。
- P2：文本收发、分页/游标、去重、客户稳定身份、人工暂停/恢复、代际隔离、并发和故障状态。
- P3：客服账号真实同步/增改删、链接、项目绑定、管理页面及审计。
- P4：媒体、恢复、Windows 运行、真实企业微信 E2E、发布验收。

每个切片都必须提交：需求编号、影响的接口/状态、修改文件、测试命令、原始覆盖率、未测项和外部证据链接。

## 3. 关键日志标准

### 必须记录

- `trace_id`、事件时间、模块、操作名称和结果状态
- binding/project revision、customer generation、inbox/outbox/operation 标识
- 必要的脱敏外部标识，例如 `open_kfid` 的短哈希或有限长度 ID
- 状态转换：`HTTP_ACCEPTED`、`UPSTREAM_ACCEPTED`、`DELIVERY_UNKNOWN`、`HELD`、部分发送和后续失败
- 错误类别、重试次数、截止时间是否耗尽、游标是否有进展
- 启动、关闭、迁移、恢复、人工接管、同步暂停及健康状态

### 严禁记录

- Token、Secret、access_token、通知 token、Cookie、Authorization、主密钥及任何完整凭证
- 客户正文、回答正文、媒体内容、原始 XML/JSON、可复原的加密载荷
- 无限 cardinality 的客户 ID 指标标签
- 通过 query string、异常堆栈或第三方库日志间接泄露的密钥

日志必须是结构化事件。错误日志也要经过同一套脱敏函数；脱敏测试要覆盖字面量、URL query、转义 query、嵌套 map、错误包装和二进制值。日志失败不得导致业务二次失败，但关键外部操作必须保留可审计状态。

## 4. 发送和人工接管不变量

- 回调返回 HTTP 200/202 只表示网关接受了通知，不代表 AI 已处理或客户已收到。
- 一页同步数据与游标必须在同一数据库事务中提交；重复通知必须幂等；游标不前进时必须停止并报警。
- 外部请求响应丢失时记录 `UNKNOWN`，默认不自动重发；不得把“没有看到回复”推断成“没有发送”。
- 发送前再次检查绑定 revision、客户 generation、人工状态、窗口和预算。人工状态未知或查询失败时默认不发。
- 人工恢复创建新 generation；旧 generation 永远不能重新获得发送权。
- 数据库事务不能跨网络调用；网络调用必须有截止时间；不允许用长事务或全局锁等待 AI。

## 5. 测试门禁

本项目使用 Go 语句覆盖率，整体和每个业务模块都必须严格大于 95%，不是大于等于 95%。判定使用整数比较：`100 * covered > 95 * total`。覆盖率不能通过排除业务代码、删除失败用例、稀释模块或改统计边界获得。

至少执行：

```sh
go test ./... -count=1 -race -covermode=atomic -coverpkg=./... -coverprofile=coverage.out
go tool cover -func=coverage.out
go vet ./...
```

测试必须分层：

- 单元：验签、加解密、字段校验、状态迁移、分段、预算、代际和错误分类
- SQLite 集成：迁移、事务、幂等、重复页、无进展、进程中断和恢复
- cc-connect 契约：未修改固定版本客户端的 HTTP/XML 交互，不得只用同一套 fake 自证
- 并发：同项目不同客户、不同项目客户、慢客户 A 与快速客户 B/C 同时处理，验证无全局串行和无串话
- 安全/故障：跨绑定、旧 generation、人工竞态、SSRF、日志泄密、响应丢失、部分发送和磁盘错误
- Windows/真实 E2E：单独记录，不能以 Linux 单元测试或交叉编译代替

覆盖率检查器本身要测试 94.99%、95.00%、95.01%、空报告、损坏报告、缺失生产包、重复 profile、路径含冒号和源版本不一致等失败闭环。

## 6. 外部接口和证据纪律

使用微信客服官方文档、固定 SDK 源码和实际企业权限时，记录来源、读取日期、适用字段和仍待核验内容。搜索摘要、博客、fake 返回值和代码注释都不能当作最新官方政策。真实客服账号、真实发送、生产部署和破坏性操作必须单独授权并使用测试企业/最小权限。

## 7. 完成定义

只有在以下证据齐全后，才可以说“首版完成”：

- 代码、配置、迁移、日志和错误状态已实现
- 本地测试通过；GitHub Actions 在干净环境通过 lint、vet、race、全量测试和严格覆盖率门禁
- 整体、每模块和关键安全/路由/状态场景达到门槛
- Windows 实际运行、未修改 cc-connect 双向契约、真实企业微信文本 E2E、人工接管完整周期和 AT-070 并发证据齐全
- 发布报告列出命令、版本、提交 SHA、原始覆盖率、失败/未测项和限制

在上述证据不齐全时，只能准确描述为“文档完成”“代码切片完成”或“CI 通过”，不能宣称生产可用。
