# 架构决策：最小可靠实现基线

- 日期：2026-10-09
- 状态：唯一现行设计；业务功能待实现，具体工具版本在首次实现时固定。
- 关联：[需求](../01-requirements.md)、[总体架构](../02-architecture.md)、[技术评审](../15-feasibility-review.md)。

## 1. 独立 HTTP 网关

采用微信客服 → 网关 → 未修改 cc-connect → Codex，复用现有 WeChat Work 手动配置和高级 api_base_url。网关提供 gettoken、user/get、message/send、媒体等必要兼容接口，同时向客户端回调 URL 投递加密 XML。

网关必须实际可达客户端回调，不把 API 地址当反向隧道。同机不同 HTTP 平台实例避免端口冲突。两侧凭证和身份分离。拒绝智能机器人 WSS 替换、OneBot、个人微信扫码、新增 cc-connect 平台插件或定制客户端源码。

网关不调用模型、不启动或管理 Codex、不管理其工作目录和模型凭证；原模型及中转站配置保持在执行端。

## 2. 单进程并发服务多客户

首版单企业、单实例、单网关进程；在该进程内并发处理不同客户。**单进程不是单客户，也不是等待客户 A 的整轮 AI 完成后才能处理 B。** 一个客服/一个 binding 可以服务多个独立客户会话。

不同客户独立 UID 与任务；同 scope 游标、同会话状态/代际/发送预算只做必要的局部串行。数据库锁和全局互斥不得覆盖网络等待或整轮 AI。网关投递完成后释放投递 worker，回答通过独立 HTTP 请求返回。

worker 限制是对应网关任务的资源保护，不是客户数或整个系统的 AI 会话上限。cc-connect/Codex 独立运行，其并发能力、配置、服务器资源和平台限制以实际 AT-070 联调为准。保留有界排队/限流，不承诺无限并发，不写死客户/客服/项目的业务数量。

## 3. SQLite 与少量后台任务

SQLite 保存 Inbox/游标、Outbox、身份代际、人工暂停、操作结果和必要审计；内存队列只作唤醒。单实例启动互斥，不设计跨实例抢占租约、分布式锁，不引入 Redis、Kafka、消息中间件或 Kubernetes。

一页数据与游标同事务；网络 I/O 不跨数据库写事务。发送前保留可恢复记录，明确未知结果，不将所有中断状态无条件重置待重试。逻辑职责不要求一个职责一张表或一个表一个包；允许合并存储，但不能丢掉唯一约束、授权范围、代际、UNKNOWN 和恢复证据。

## 4. 小型中文管理

同进程服务端渲染 HTML 和少量表单即可，保留真实客服同步、创建、编辑、删除、链接、绑定、凭证、启停、接管状态和诊断。只有官方成功才显示真实操作成功，不以本地配置 CRUD 代替客服账号管理。

首版单管理员角色即可，不建租户注册、复杂 RBAC、公共 REST 平台、独立 SPA、坐席聊天、工单、排班或计费。管理读取均鉴权，写入具备 CSRF、对象范围、revision、防重复提交和必要审计；删除另做明确二次确认。

管理写入优先有界同步执行，保留操作记录用于崩溃和 UNKNOWN 核查；只有确实不能及时完成的工作才后台处理。无需统一异步 202 编排或通用任务框架。

## 5. 身份、人工接管与问答权限

稳定 customer_id + binding + generation 对应兼容 UID；正常对话稳定，人工恢复/改绑换代际。旧 UID 永不再具备发送资格，恢复将创建新的客户端上下文。发送前核查官方状态和本地人工栅栏；事件缺口时保守暂停，已在途请求无法保证撤回。

客户控制命令限制、持久化、人工暂停/代际及发送预算先于对外文本试用。只读需要客户端配置、Codex 与 OS 共同落实；UID 只解决会话路由，不证明客户文件保密隔离。公共客服仅接入可共享资料，敏感附件需通过独立权限验证。

## 6. 实现栈与质量

推荐 Go、SQLite 和内嵌 HTML，使用标准 HTTP/JSON/XML/密码库，必要依赖少量、固定版本并审查许可证。语言不是用户指定；首次实现一次性记录工具链、驱动、Windows 条件与覆盖率映射。用户选择其他栈时同步修改唯一现行设计，不并列维护互相冲突的实现方案。

R-001～R-024、真实账号管理、昵称、媒体目标、人工接管和安全全部保留。整体/每业务模块/规定差异语句严格 >95%；自写前端统计按测试文档执行；关键场景全部通过。可用小脚本做门禁，不先建设通用测试平台，不排除业务代码刷指标。

## 7. 验证与边界

固定源码、SDK 注释、官方/企业核验和真实运行结果分开记录。按能力切片核验并推进内部开发，相应真实功能发布前确认权限/契约和联调。不承诺 exactly-once、重启历史补答、昵称即时刷新、客户已读或跨人工代际无损续聊。

默认一个实现者顺序推进小任务，不要求多 Agent 团队；这不限制产品的多客户运行并发。只有实际瓶颈或明确新需求才新增组件。文档直接维护当前正文、来源和验收，不另保存修改记录、历史修订附录或并行旧方案；正常 Git 提交历史保留。
